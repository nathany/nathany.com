[Jobber][] provides business management software (calendaring, invoicing, etc.) to field service companies, such as landscapers, maid services, or pretty much any vertical involving on-site work.

Last October I joined the two founders to continue building the product. This month our *team of eight* is moving into a renovated 2000 sqft office to accommodate our growth.

## First Sight

Edmonton has a [vibrant startup scene][startupyeg], so what attracted me to Jobber?

* I wanted to taste the startup life, but still take home a salary.
* Jobber had already found product-market fit as SaaS for small business. It was just a matter of scaling up.
* The opportunity to work on [mapping](http://www.google.com/intx/en/enterprise/earthmaps/maps.html) and [mobile][jqm] was compelling.
* *Ruby on Rails:* I have been using Rails for 6+ years now. I had no interest in  PHP or even Node.js. Every once in a while I work on a WordPress site or similar to remind myself of how nice Ruby is.
* *Heroku:* I've spent enough time doing deployment to appreciate having someone else to keep the servers running while I focus on programming.

## Moving Fast

While I have been responsible for a lot of feature development, I'm going to focus on the infrastructure and performance improvements I made, which may be of use to other Rails developers.

### Unicorn

We made [Unicorn][] our app server about 9 months ago. This required a lot of research to get the [configuration](https://gist.github.com/nathany/5058140) just right.

Once our app is fully loaded, it uses about ~300MB of memory. We were an early adopter of Heroku's double dynos, which provide enough RAM to run 3 Unicorn workers per dyno (Unicorn uses a process model). If being able to handle 3 concurrent requests sounds pathetic, *it kinda is,* but there are two other factors to consider: 

* The faster we can complete requests (in milliseconds), the more we can handle. 
* We can run as many dynos as we need, and we pay Heroku a lot of money to do just that.

Overall Unicorn has been a good move. I mean, it's good enough for GitHub, right? Double dynos have been a life saver for two reasons:

* The servers are able to handle 3x the requests for only 2x the price of regular dynos.
* Our servers are less sensitive to long running requests. It takes 3 slow requests all randomly pushed to the same dyno before a 4th request will queue.

We had high hopes for Ruby 2.0's copy-on-write friendly GC. Would we have room for another Unicorn worker? Maybe two? Well, not so far. I'm sure we'll end up moving to a threaded model within the next year, but this is working well enough for now.

### Asset Sync

Given the $72/month we pay per dyno, it makes no sense to waste those resources serving static JavaScript, CSS and images. Last year I setup [asset_sync][] to serve our assets from S3.

It's fairly straightforward to setup, just be sure to keep existing remote files and avoid non-digest assets if you ever want to rollback a deploy. 

To ensure a consistent view of your app and its assets, Heroku recommends pointing your CDN (i.e. CloudFront) directly at your dynos rather than using asset_sync. So far I've had little success in switching to this method, YMMV.

We did run into one tricky issue with Internet Explorer 9. Anytime we did an Ajax request that returned HTML, any embedded JavaScript would fail to bind. An example would be a dialog box that made use of `link_to_function` for the cancel button.

Once we we're able to correlate serving assets from a separate domain with buttons not working in IE, the first step was to better simulate the production environment:

```ruby
# use a different domain for assets (development.rb)
config.action_controller.asset_host = "http://s3.dev:3000"
```

Thankfully the solution wasn't a crazy IE-specific hack. Rather, moving to Unobtrusive JavaScript got IE9 working and improved our code too.

## Why I &hearts; My Jobber

I work and play (foosball) with a great group of guys. Some say "be the worst", that is, work with people smarter than you. I'm not sure that worst is best. I'm learning and mentoring, it goes both ways.

The team gets product design. We aren't afraid to say "no" to our customers. We understand that people do want features, but we balance that with keeping the UI simple for newcomers. Our add-ons are pivotal in catering to many different companies.

Quality is the focus. We don't set arbitrary deadlines, and often I am able to work on one thing at a time (think Kanban). Once a feature is complete, I almost always spend some time refactoring the code, to make it easier to understand and change in the future. We make heavy use of GitHub pull requests for code review, and pair program as the need arises.

We are always upgrading. Our app is using the latest Ruby 2.0 and though a few dependencies keep us from upgrading to Rails 4, I was beginning to prepare for its arrival a year ago. Faster asset compilation and support for additional PostgreSQL data types are two enhancements I'm looking forward to. Local developers who are *[stuck in Kansas](http://www.youtube.com/watch?v=yhseQP52yIY&t=13m16s)*, you'll [find us][jobs] if you keep heading west. :-P

With flex-time, I often work from 10 to 6, and if I'm feeling under the weather, I can work from home.
