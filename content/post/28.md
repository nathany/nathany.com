Hop in Your DeLorean and rewind the clock to the summer of 1997. I had just landed my first job as a web developer. HTML 2.0 and images, nothing more.

A few years pass. As the turn of the century approaches, we're utilizing JavaScript and ColdFusion to make websites *dynamic!* But there were no automated tests and no "cloud" to deploy to. We didn't even have version control, and collaboration among developers was minimal.

A lot has changed.

> "the job of the software engineer is constantly being reinvented..." 
> 
> \- Keven Scott (Microsoft CTO) via <a href="https://www.youtube.com/watch?v=GclIFNftjzA" class="fab fa-youtube fa">Tiff in Tech</a>

Today our team works remotely thanks to tools like Zoom, Slack, GitHub, and [Shortcut][]. We use test-driven development (TDD), distributed version control, code reviews, and continuous integration. We rely on open source and deploy Docker containers to the cloud.

When deciding *what* to build, we can hop on a video call, share our screens, and collaborate. We'll reach for a Generative AI model, such as [Claude Sonnet 4][], with questions on *how* to best write or optimize code, to avoid a tedious task, or just out of curiosity. When pushing code, [CodeRabbit][] (AI) will be the first to request changes, occasionally catching bugs that human reviewers may not spot.

The tools and technologies have changed over time, but not all changes are equal. At times we replaced one tool with another, but we still accomplished similar results in similar ways. At other times, our way of working fundamentally shifted.

* Improving collaboration among developers
* Increasing confidence in our changes through automated tests
* Less time chasing down trivial bugs thanks to continuous integration

## Mistakes were made

As I reflect on the past 28 years, I thought it would be fun to share some of my *biggest fails*, along with how I would avoid them today. We have a lot of tools at our disposal that can help prevent mistakes, but only if we put them into practice.

*Note: As some of these stories are from decades ago, I may not have all the details right, but this is how I remember them.*

### That time I deleted the users table

That day I was assigned the task of cleaning up the `users_archive` table. Why we had this table, I don't know, but apparently it was getting big. I was to delete some of the rows.

While writing the SQL queries -- directly on production -- the CTO came by my desk and asked for a different query. A query that required the `users` table.

I think you can see where this is going. 😬

My wires got crossed, and I ended up running my "cleanup" query against the wrong table.

People in the office started asking why production was down. With thousands of active users, deleting a large number of rows from a fundamental table like `users` was a struggle for the database.

That struggle was a blessing in disguise. Once I realized my mistake, I was able to cancel the query. Though by no means instant, the transaction rolled back, as if the data was never deleted.

I had caused a temporary outage, but no data was lost. Crisis averted!

#### Lessons learned

For me, the main lesson is to avoid multi-tasking, especially when making changes on production. Many of my mistakes were caused by doing too many things at once.

To avoid similar mistakes:

* I have a to-do list for each day, so I can add a request to my list and come back to it later, instead of jumping back and forth.
* By working remote, I can *choose* whether to be interrupted by a Slack notification, or to wrap up what I'm doing first.
* Generally I prefer to avoid mutating data directly in production. If the problem isn't urgent and can be solved with a data migration, then it will go through the regular code review and deployment process. That can help avoid mistakes.
* When I log into production, I use the Red Sands theme in Terminal to clearly demarcate it from a local shell. For database access, [TablePlus][] can be configured with a red status color too, though I wish it were more prominent.
* I always shutdown my connection to production as soon as I'm done, to avoid using the wrong server by accident.
* Though not mandated, I do think it's a good idea to pair program whenever mutating production data directly.
* For my local database, when I write a DELETE or TRUNCATE query in a SQL file, I will write it as a comment. That way it must be selected to run, so accidentally *running all queries* won't delete things!

### Too many pending transactions

It was a rough time for the company. Our payment gateway didn't support verification numbers (CVV/CVS) or address verification (AVS). We had lost access to our merchant account due to an uptick in scammers, but the paperwork hadn't gone through to get a new payment gateway that would support CVS and AVS to help block the fraud. In the meantime, the best we could do is store the encrypted card information for later.

I was new to working with payment gateways, much less the system that was in place. But I was assigned to work on it during this transition.

Though I don't remember the specifics, I do remember fixing a bug -- or so I thought. 🤦🏼‍♂️

After deploying my "fix", I caught up with the other developers who were heading out for lunch. It was a lengthy lunch too.

When I finally got back, I got an earful. Something about "pending transactions" -- whatever those were? A little shaken, I immediately got to work. As it turned out, I had turned a small bug into a bigger nastier bug! 🦟

Later I learned what a pending transaction was -- it's actually pretty clever. Whenever a purchase was made, a database record was stored that was marked as pending. This was before the request to the payment gateway. After the gateway responded, the transaction was marked as approved or declined, but no longer pending.

If the number of pending transactions exceeded a threshold, emails would be sent. That either meant that the payment gateway was not responding or there was a bug in our code. Unfortunately, I was *out to lunch,* with no cell phone and no idea.

#### Lessons learned

* Never deploy right before leaving
* Monitoring is a valuable time investment
* Take the time to share knowledge and good practices

To avoid similar mistakes:

This mistake occurred years before automated testing was common practice. However, the knowledge of unit tests and TDD is insufficient on its own. We still need to actually write the tests, even when there is a seemingly urgent bug in production!

Taking 5-10 minutes to write a failing test won't only prevent a regression from reintroducing the bug in the future, it may prevent introducing another "new and exiting" bug as part of the "fix".

### Accidentally invoicing a military airbase

As is fairly common, we had a few different environments. Local development servers, a QA environment, and production. If I recall correctly, QA was a clone of production.

I was deploying our work, and decided to do some last minute manual testing. Everything worked fine, and I didn't even realize my mistake until it was brought to my attention the next day.

With so many browser tabs and windows open, it was an easy mistake to make. Using the wrong environment. The manual testing I had done triggered some emails, and those emails went to a real user! Not just to a customer, but to a customer's customer. This was bad. This was very bad. 🤦🏼‍♂️

#### Lessons learned

To avoid similar mistakes:

We made some changes after that event. Firstly, to clearly demarcate QA and development environments, so it was obvious which server we were looking at.

We also found a service that could prevent emails sent from QA or development from sending to the end user.

These days, we don't consider it a good practice to make QA a replica of production data. We want the data in QA to be *representative*. That is, we want enough data for testing load and so forth, but there is no contact information outside of our own company on the QA servers.

In addition, to combat the explosion of browser tabs:

* I make judicious use of [OneTab][] to collapse tabs I'm not using
* Use separate browser windows for production/QA to segregate them from development tabs
* Use a dedicated documentation browser like [Dash][] and other desktop apps to reduce how many browser tabs I need in the first place

### The colleague who was popular with the ladies

*This isn't one of my own fails, but it's a fun one, so I'm going to share it anyway.*

My colleague was working on a new real-time chat feature for an online dating website. When he deployed his changes, he had forgotten to remove some debug code.

Shortly after he got a request to chat. And then another request. And another. Pretty quickly he realized that this was a little unusual.

While testing locally, he had all the requests go to his profile. That was useful locally, but it wasn't intended to go to production. Whoops!

#### Lessons learned

What is the lesson here? Working for an online dating company has its perks? 😅

To avoid similar mistakes:

* Automated tests and continuous integration would've caught it.
* These days we have configurations for each environment, so a chat debug mode could be a permanent option, one that could only be activated locally.

## In summary

It goes without saying that I've made numerous mistakes throughout my career, these are just a few. And I'm not naive enough to think that I won't make more mistakes in the future, both as a software developer and as a human.

If you're afraid of failure, all I can say is that I managed to hold onto this career despite some pretty serious blunders. Just do your best. Nobody is perfect and nobody should expect perfection.

I hope by giving you a glimpse into the past, this article gave you a greater appreciation for the tools that can help prevent bugs today. At the same time, I hope you recognize that tools alone aren't sufficient. Sometimes improving our own process of working is the only thing we can do.
